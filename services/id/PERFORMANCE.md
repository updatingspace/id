# План ускорения ID и запросов Portal

Проверка 22 сентября 2026 года. Источники: активные ревизии YC, серверные логи ID,
код ID и локальная копия Portal, ограниченные чтения production YDB. Данные аккаунтов,
SQL-параметры, session tokens и секреты в результаты измерений не включены.

## Что уже установлено

Основная часть задержек на предоставленных скриншотах возникает внутри приложения.
В выборке логов ID обработка входа заняла 2331 мс, медиана списка сессий — 756 мс,
статуса MFA — 429 мс, списка passkey — 289 мс. Выборка небольшая: 1–5 запросов на
endpoint; это диагностика конкретных обращений, не устойчивые p95/p99.

| Активный HTTP-контейнер | CPU / память | Concurrency | Готовые экземпляры |
|---|---|---:|---:|
| ID backend | 1 / 1024 МБ | 8 | 1 |
| Portal BFF | 1 / 1024 МБ | 8 | 0 |
| Portal, access, activity, events, voting, gamification | 1 / 512 МБ каждый | 8 | 0 |
| Featureflags | 1 / 256 МБ | 8 | 0 |
| ID Gravatar, фоновая задача | 1 / 512 МБ | 1 | 0 |

Это инвентаризация текущих лимитов, а не рекомендация выделять столько каждому
сервису. Бюджет — ограничение плана: сначала сокращать лишнюю работу, затем
подбирать минимальные ресурсы с измеренным запасом.

## Бюджетный профиль для проверки

| Сервис | Кандидат RAM | Готовые экземпляры | Условие принятия |
|---|---:|---:|---|
| ID | сначала сохранить 1024 МБ | 1 | Проверить 768/512 МБ отдельно: 4 процесса и обработка аватаров дают пики |
| Portal BFF | 512 МБ вместо 1024 | сначала 0; затем 1 при заметной цене холодного старта | Измерить пик на 8 одновременных прокси-запросах, включая streaming |
| Portal, access, activity, events, voting, gamification | 256 МБ вместо 512 | 0 | Пройти собственный сценарий сервиса, запуск и параллельную нагрузку |
| Featureflags | сохранить 256 МБ | 0 | 128 МБ рассматривать только после замера, не назначать Django-сервисам вслепую |
| Gravatar | сохранить 512 МБ до отдельного замера | 0 | Декодирование/resize изображений может требовать больше памяти, чем обычные API |

Это кандидаты для стенда, не подтверждённые безопасные production-лимиты.
Для снижения памяти нужны пиковое потребление процесса/контейнера, запас около
30%, отсутствие OOM и ухудшения p95. Среднего RSS недостаточно. Для простоя
с `min_instances=0` постоянно оплачиваемый подготовленный экземпляр отсутствует;
поэтому прогрев всех сервисов может стоить больше, чем экономия RAM.

Уменьшение 512 → 256 МБ не означает двукратное снижение всей цены. При прежнем
времени выполнения и 1 vCPU компонент RAM уменьшается вдвое, компонент CPU
остаётся. По опубликованной рублёвой формуле после free tier цена активного
вычислительного часа меняется примерно с 7,585 до 6,638 ₽, то есть на 12,5%;
вызовы, сеть и прочие сервисы считаются отдельно. Ускорение запроса уменьшает
оплачиваемое время обоих ресурсов. Это пример, не прогноз месячного счёта.
[Тарификация YC](https://yandex.cloud/ru/docs/serverless-containers/pricing).

Число `1 vCPU` не означает отдельную работающую круглосуточно VM на сервис.
YC выделяет CPU при обработке вызовов; простой подготовленного экземпляра
имеет отдельную тарификацию. Для I/O-нагрузки можно отдельно испытать меньшую
гарантированную долю CPU, но замедление Python, криптографии и старта способно
съесть экономию. Повышение до 2 vCPU в YC требует минимум 4 ГБ RAM, поэтому
это не бюджетный следующий шаг.
[Ресурсы среды выполнения YC](https://yandex.cloud/en/docs/serverless-containers/concepts/runtime).

У ID уже есть подготовленный экземпляр и повторное использование соединений
с БД (`CONN_MAX_AGE=600`, пул YDB DBAPI размером 5 на соединение). Создавать новый
пул на каждый запрос или просто увеличивать его размер не требуется.

У Portal подготовленных экземпляров нет. Первый запрос после простоя может
ожидать запуск BFF и затем нужного внутреннего сервиса. В локальном Terraform
Portal уже задан default `min_ready_instances.bff=1`, но активная ревизия BFF
этого не содержит: нужно проверить фактические tfvars и выкладку Portal.
Локальный код Portal не следует считать доказательством содержимого старой
production-ревизии.

Подготовленные экземпляры устраняют холодный старт только в пределах своей
ёмкости; при масштабировании дополнительные экземпляры могут запускаться
холодными. Простой подготовленных экземпляров оплачивается отдельно.
[Документация YC](https://yandex.cloud/en/docs/serverless-containers/concepts/container).

## Изменения ID в этом выпуске

| Операция | Было | Стало |
|---|---|---|
| Чтение списка сессий | 2 + N SQL, отдельно срок каждой сессии | 3 SQL независимо от N; 2 для пустого списка |
| Статус MFA | 3 SQL | 1 SQL |
| Чтение сессии по X-Session-Token | exists + load | одна загрузка с проверкой срока действия |
| Диагностика | общая длительность в логах | дополнительно количество и время SQL, `Server-Timing` |

Стратегия сессий не кеширует авторизацию между HTTP-запросами. Каждый lookup
читает актуальную сессию; удаление, истечение срока и неактивный пользователь
по-прежнему запрещают доступ. Предварительная сессия с challenge для passkey
сохраняется. Загрузка списка сессий сохраняет признаки current/revoked и
изолирует пользователей.

Ограниченный замер тех же сервисных функций с реальной production YDB
из рабочей Linux VM, без изменения данных: три чтения до и три после, ниже
диапазон двух повторных чтений после первого прогрева.

| Чтение | До | После | SQL до → после |
|---|---:|---:|---:|
| Сессии | 220–229 мс | 101–107 мс | 6 → 3 |
| MFA | 77–79 мс | 36–41 мс | 3 → 1 |
| Email, контроль без изменений | 34–42 мс | 31–37 мс | 1 → 1 |

Это ускорение соответствующей части серверной работы, не обещание двукратного
ускорения всего HTTP-запроса. В эти числа не входят браузер, Cloudflare, API
Gateway, middleware авторизации и очередь Gunicorn. Ускорение стратегии сессий
отдельно подтверждено бюджетом запросов: сессия + пользователь требуют 2 SQL
вместо 3. Сквозные цифры нужно сверить после выкладки по одинаковым endpoints.

`Server-Timing` содержит `app;dur=...` и `db;dur=...` в миллисекундах. В логах
добавлены `db_query_count` и `db_duration_ms`. SQL и значения параметров не
логируются. `db` измеряет Django default connection, включая ожидание ответа
БД; прямые вызовы SDK в YDBCache, SMTP и внешние HTTP-вызовы в него не входят.
Разность browser TTFB и app — смесь сети, прокси и ожидания перед приложением,
а не чистая оценка холодного старта.

## Следующий порядок работ

1. **Подтвердить эффект ID на обычном трафике.** Собирать по каждому endpoint
   p50/p95, статус, app/db и число SQL; связывать по request_id и revision_id.
   Раздельно смотреть первые запросы новой ревизии, после простоя и прогретые
   серии. Для повторяемого стенда: 1, 4 и 8 параллельных запросов, одинаковые
   синтетические пользователи, без отправки реальных писем и без нагрузочного
   теста production. Сравнение после смены пароля/отзыва сессии обязательно.

2. **Portal: подготовить BFF и наиболее частые зависимости.** Начать с одного
   BFF, затем по трассам решить, нужны ли постоянно готовые access и portal.
   Для внутренних сервисов Terraform пока не применяет карту готовых
   экземпляров; одного изменения переменной недостаточно. Редко используемые
   сервисы и фоновые задачи оставить с нулевой готовой ёмкостью. Перед rollout
   проверить квоту и стоимость дополнительной готовой памяти. Настройки ID
   в этом выпуске ресурсов не увеличивают.

3. **Portal: повторно использовать HTTP-соединения BFF.** В локальном
   `services/bff/src/bff/proxy.py` на каждый проксируемый запрос создаётся и
   закрывается `httpx.Client`; OAuth callback использует отдельные `httpx.post`
   и `httpx.get`. Ввести ограниченный пул на процесс и таймауты подключения/
   чтения/ожидания пула. Не хранить в общем клиенте пользовательские cookies,
   Authorization или tenant headers; передавать их отдельно на запрос.
   Сохранить HMAC, IAM, запрет redirect и закрытие streaming responses.
   Измерить DNS/TCP/TLS и ожидание upstream до/после. IAM-токен уже кешируется;
   повторный кеш для него не нужен.
   [HTTPX: connection pooling](https://www.python-httpx.org/advanced/clients/).

4. **Вынести SMTP из критического пути входа.** Сейчас предупреждение о новом
   устройстве отправляется синхронно из `ActivityService.record_login`.
   Добавить durable outbox и обработчик YMQ: запись задания вместе с событием,
   повторы с backoff, дедупликация и наблюдаемая ошибка доставки. Не заменять
   это фоновым потоком внутри serverless HTTP-контейнера. Ссылки восстановления
   и подтверждения должны оставаться одноразовыми; измерять задержку до доставки
   и не выдавать успех при потере задания. Это отдельная миграция, не часть
   текущей оптимизации чтения.

5. **Ресурсы и Gunicorn менять по профилю нагрузки.** ID сейчас допускает 8
   concurrent invocations при 4 sync workers: возможна очередь внутри
   контейнера. Но проба 2 процессов × 4 gthread не дала стабильного улучшения.
   На read-only проверке отсутствующей сессии, 32 запроса при параллельности 8
   после начального прогрева, sync4 дал медиану 50,9 мс / p95 76,6 мс;
   gthread2×4 — 43,7 / 1075 мс. Замер выполнен локально с реальной YDB, не на
   CPU-лимите YC, и не имитирует полный вход. Этого недостаточно для перевода
   production на потоки. Проверить несколько волн полного сценария на стенде,
   время первого открытия пула каждым потоком, CPU/RSS и очередь. Сравнить
   sync4/concurrency4, текущий sync4/concurrency8 и gthread2×4 на 1 CPU.
   Выбирать по хвостам задержек и стоимости, а не только средней скорости.
   [Модель Gunicorn](https://docs.gunicorn.org/en/stable/design.html),
   [размер пула YDB](https://ydb.tech/docs/en/recipes/ydb-sdk/session-pool-limit).

6. **Кеш и индексы — после профиля.** YDBCache выполняет отдельные транзакции
   для form tokens/rate limits. Измерить их вклад трассировкой до подключения
   платного Redis/Valkey. Одноразовое потребление и rate limits должны оставаться
   атомарными между экземплярами. Для частых фильтров/сортировок проверить планы
   YDB и чтение строк; не добавлять индексы по одному времени HTTP-ответа.

Предлагаемые цели для следующего замера: прогретые чтения аккаунта p95 ≤400 мс,
прогретый вход p95 ≤1500 мс, отдельный учёт первого входа с письмом. Это цели,
а не достигнутые показатели. Увеличение ресурсов принимается только при
устойчивом улучшении p95 без роста ошибок и с известной стоимостью.

## Проверка и откат

Регрессионные тесты фиксируют число запросов, MFA/recovery codes, наличие и
отзыв сессии, истечение срока, неактивных пользователей и предварительное
состояние passkey. Полный backend suite и coverage gate, интеграция с YDB,
Postgres и общий CI остаются обязательными перед merge.

Текущие изменения не требуют миграций БД и не меняют формат session tokens.
Откат — предыдущая ревизия приложения и соответствующий commit; существующие
сессии совместимы. Будущие изменения ёмкости выполняются через Terraform с
сохранением предыдущих значений и сравнением метрик после раскатки.

## Инициализация маршрутов HTTP-процессов (2026-09-23)

В свежем процессе локальный cProfile показал 762 мс на первый `/healthz`,
основная работа — импорт дерева URL и API. Следующие гостевые `/auth/me`
заняли 3,7 и 2,2 мс. WSGI entrypoint теперь материализует дерево URL при
инициализации каждого worker. Тот же локальный сценарий после изменения:
20,3 мс на первый `/healthz`, 5,9 и 2,1 мс на `/auth/me`.

Изменение переносит ленивую загрузку до обслуживания запросов. Оно не уменьшает
время запуска самого процесса и не является гарантией сетевого SLA: остаются
запуск контейнера, очередь и сеть. Gunicorn master не загружает приложение
заранее, поэтому SDK/telemetry threads не переносятся через fork. Соединения с
БД этим изменением не открываются и данные не запрашиваются.

Новый тест запускает изолированный Python-процесс, запрещает создание соединений
Django DB, загружает WSGI entrypoint и проверяет реальные WSGI-ответы `/healthz`
и гостевого `/auth/me`, включая `private, no-store`. Полный CI остаётся gate.
Внешний порог строго <500 мс для всех функций пока не подтверждён.

## Справочник часовых поясов (2026-09-23)

В последовательном HTTP/2 замере первый `/auth/timezones` занял 982 мс,
`Server-Timing app` — 815 мс, DB — 0. Последующие ответы: 251, 164, 154 мс.
Определения pytz теперь загружаются при подготовке WSGI worker; публичный
справочник кэшируется на текущую минуту UTC с одним элементом в кэше. Он не
содержит пользовательских данных и возвращается новым списком. Следующая
минута пересчитывает смещения, включая переходы DST.

Заодно исправлены отрицательные дробные смещения (St Johns в сентябре:
`-02:30`, раньше ошибочно `-03:30`). Все зоны рассчитываются от одного реального
UTC-момента, поэтому неоднозначное/несуществующее местное время не удаляет зону
из списка при переходе DST. Регрессии проверяют отрицательные и четвертьчасовые
смещения, оба перехода DST, неизменяемость кэша и реальный WSGI-ответ без БД.

## Пустой список внешних OAuth-провайдеров (2026-09-23)

В ревизии 5a2289e публичный список пуст и приложения внешних allauth-провайдеров
не установлены. Однако `list_providers()` сначала запрашивал SocialApp в YDB,
а затем пересекал результат с пустым реестром. В предыдущей внешней выборке
endpoint занял 508/432/354/164 мс; SQL — 66/51/29/19 мс. Остальная задержка этим замером не разделена
на инициализацию соединения, приложение и сеть.

Теперь отсутствие установленных реализаций проверяется до чтения настроек из
БД: ответ остаётся `{"providers": []}`, но не требует соединения с YDB.
При непустом реестре настройки по-прежнему читаются на каждом запросе, изменения
конфигурации не кэшируются, ошибки БД не скрываются. Регрессии проверяют публичный
HTTP-ответ при недоступной БД, появление реализации после пустого реестра,
включение/отключение настроек и распространение настоящих ошибок БД.
