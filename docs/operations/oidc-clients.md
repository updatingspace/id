# OIDC-клиенты: операторские команды

`idctl` создаёт клиентов, показывает их настройки и заменяет секрет конфиденциального клиента. Команды не меняют разрешённые переходы и права уже существующего клиента, issuer, subject или ранее выданные токены. Они не открывают публичный интерфейс администрирования. Текущая CLI рассчитана на операторский Unix-хост.

Для выбранного окружения нужны обычные настройки YDB и действующие `DJANGO_SECRET_KEY`/fallback keys. Оператор должен быть одновременно `staff` и `superuser`, иметь MFA и текущую сессию ID с подтверждённым MFA. Перед каждой операцией проверяется его пароль; перед записью транзакция повторно проверяет сессию, identity, аккаунт, MFA, роль и пароль. Доступ к YDB или IAM сам по себе не заменяет полномочия оператора в ID.

Сессию и пароль передавайте только через отдельные файлы с доступом владельца (`0600`), без завершающего перевода строки. Не помещайте их в аргументы команд, историю shell, задачи или общие логи. Файл конфигурации клиента не содержит секретов; лишние поля вроде `client_secret` отклоняются.

## Создать клиента

Пример `client.json` для конфиденциального клиента:

```json
{
  "client_id": "example-rp",
  "name": "Пример приложения",
  "description": "Отдельно проверенное приложение",
  "redirect_uris": ["https://rp.example.invalid/api/v1/auth/callback"],
  "allowed_scopes": ["openid", "profile", "email", "offline_access"],
  "grant_types": ["authorization_code", "refresh_token"],
  "is_public": false,
  "is_first_party": false
}
```

`client_id` и redirect URI сравниваются точно, без wildcard. Redirect должен использовать HTTPS; HTTP разрешён для loopback-разработки. Фрагменты, встроенные credentials и дубли адресов отклоняются. В правах обязателен `openid`; `offline_access` требует `refresh_token`. Поддерживаются `authorization_code` и необязательный `refresh_token`, тип ответа — `code`. Публичному клиенту задайте `is_public: true`: секрет не выпускается, а авторизация требует PKCE. `is_first_party` включайте только после проверки соответствующих доверительных отношений.

Сначала выполните проверку без записи:

```sh
idctl oidc-client-create --config client.json \
  --operator-session-file operator.session \
  --operator-password-file operator.password
```

Команда проверит конфигурацию, оператора и отсутствие такого ID. Она не пишет данные в YDB и не создаёт файл секрета. Из отчёта скопируйте `review_digest`, после проверки примените:

```sh
idctl oidc-client-create --config client.json \
  --expected-config-digest REVIEWED_64_HEX_CONFIG_DIGEST \
  --operator-session-file operator.session \
  --operator-password-file operator.password \
  --secret-output example-rp.secret.json --apply
```

`--expected-config-digest` требуется также для публичных клиентов. Он закрепляет проверенную конфигурацию с развёрнутыми значениями по умолчанию. Порядок JSON-полей и пробелы не влияют на digest; порядок массивов и значения влияют. После любой намеренной правки сделайте новый просмотр и используйте новый digest. Этот digest относится к запросу на создание; `revision` ниже — к уже сохранённому клиенту.

Для конфиденциального клиента создаётся случайный 256-битный секрет. В YDB хранится Argon2id-хеш, а исходный секрет записывается только в новый файл `0600`. Он не выводится в stdout, stderr и audit. Существующий путь, включая symlink, отклоняется. Файл и его каталог синхронизируются до попытки записи в YDB, чтобы неопределённый ответ commit не потерял кандидатный секрет. Файл содержит `client_id`, `client_secret` и предложенную `revision`. Для публичного клиента `--secret-output` запрещён. Создание клиента и запись audit входят в одну транзакцию; существующий ID не заменяется.

## Посмотреть клиента

```sh
idctl oidc-client-show --client-id example-rp \
  --operator-session-file operator.session \
  --operator-password-file operator.password
```

Команда только читает. Она возвращает сохранённую конфигурацию и текущую `revision`, но не секрет и не его хеш. Нужны те же пароль, роль и MFA-сессия оператора. Отсутствующий или неоднозначный ID вызывает ошибку; `--apply` и `--secret-output` здесь недоступны.

## Заменить секрет

Сначала просмотрите текущую конфигурацию и `revision`:

```sh
idctl oidc-client-rotate-secret --client-id example-rp \
  --operator-session-file operator.session \
  --operator-password-file operator.password
```

После проверки примените с **новым** именем файла:

```sh
idctl oidc-client-rotate-secret --client-id example-rp \
  --expected-revision REVIEWED_64_HEX_REVISION \
  --operator-session-file operator.session \
  --operator-password-file operator.password \
  --secret-output example-rp.rotated.secret.json --apply
```

Публичный клиент, неоднозначный ID или устаревший просмотр отклоняются. `revision` учитывает сохранённую конфигурацию, ID строки, прежний хеш секрета и время обновления без раскрытия секрета. Меняются только хеш и время; audit связывает действие с оператором и не содержит ключевого материала.

После успешной замены старый секрет больше не аутентифицирует клиента. Обмен кода, refresh и отзыв повторно проверяют клиентскую аутентификацию внутри записывающей транзакции. Запрос, завершившийся до замены, может вернуть ответ позже. Ранее выданные токены живут по своим правилам: замена секрета не отзывает их. Согласуйте переключение секрета со стороной приложения.

## Если результат записи неизвестен

После timeout нельзя считать, что запись откатилась. CLI повторяет только определённый ответ YDB `ABORTED` с тем же подготовленным секретом; неизвестный commit автоматически не повторяется.

Сохраните защищённый файл секрета и вызовите `oidc-client-show` с тем же ID. Для конфиденциального клиента сравните полученную `revision` с предложенной в файле: совпадение означает, что этот кандидат сейчас сохранён; несовпадение запрещает передавать его приложению. Недоступный просмотр оставляет ситуацию неразрешённой. Новый `--apply` требует нового просмотра и нового файла. При неопределённом создании публичного клиента сравните всю конфигурацию с ранее проверенным отчётом; одно лишь существование ID не доказывает успех этой попытки.

После завершения удалите временные файлы с вводом оператора и перенесите подтверждённый секрет в хранилище приложения. CLI не публикует его в Lockbox и не меняет настройки другого сервиса автоматически.

## Локальная проверка

Интеграционный тест запускает настоящие процессы `idctl` на отдельной локальной YDB с синтетическим оператором и убирает только свои записи:

```sh
YDB_ENDPOINT=grpc://localhost:2136 YDB_DATABASE=/local \
YDB_CREDENTIALS_MODE=anonymous CARGO_INCREMENTAL=0 \
CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 \
cargo test --locked -p id-runtime --test oidc_client_operator_ydb -- --ignored --nocapture
```

Нужна заранее подготовленная legacy-схема. CI отдельно проверяет защиту commit при изменении роли, сессии и revision после предварительного просмотра, а также конкурирующее создание. Локальный тест не является разрешением запускать эти операции на рабочей базе.
