# Эксплуатация ID

## Рабочая конфигурация

Сервис работает в домашнем k3s: namespace `updspace-id`, Deployment `id`.
В одном pod находятся API, sessions, mutations, web, jobs и внутренний router.
YDB и Garage размещены в `updspace-data`. Общий HTTP/TLS Caddy принадлежит
инфраструктурному проекту; Portal имеет собственную базу и жизненный цикл.

Манифесты и production overlay: репозиторий `updatingspace/infra`,
`environments/home/id-platform/id`. Не применяйте base без overlay: base имеет
нулевое число реплик и приостановленные задания. Перед применением сравнивайте
план с текущим кластером; ручной drift нельзя затирать полным apply.

Поддержка static credentials YDB с проверкой TLS/DNS, операторского S3 endpoint
и доступа мониторинга включена в исходники. Накладывать старые
`runtime-local-services.patch` и `observability-*.patch` больше не нужно.
Секреты, ключи подписей, имена таблиц и данные не пересоздаются при выпуске.

## Выпуск

1. Зафиксировать commit, пройти CI на закреплённом toolchain. Из этого commit
   собрать `Dockerfile.api`, `Dockerfile.web`, `Dockerfile.jobs` с контекстом
   `services/id-rust`. API-образ используется контейнерами api/sessions/mutations.
2. На сервере сохранить в каталоге релиза исходники, образы, SHA256 и прежние
   digest/конфигурацию для отката. Пользовательские данные туда не экспортировать.
   Импортировать образы в containerd и закрепить точные digest, поскольку
   `imagePullPolicy: Never` требует локально доступных имён.
3. Добавить публичные `/data`, `/privacy`, `/terms`, `/contacts` к маршрутам web,
   сохранив более точные `/data/export` и API-маршруты. Согласованно обновить
   web и API: новая регистрация требует `age_confirmed=true`. Обновить jobs,
   чтобы все семейства писем использовали общий шаблон.
4. Применять ограниченный patch с проверкой UID/resourceVersion и старых
   digest. Сохранить существующие feature flags, секреты, расписания и router.
5. Дождаться готовности всех контейнеров. Проверить полную загрузку новых
   страниц и ресурсов, OIDC discovery, отказ анонимному UserInfo и закрытым
   операциям. Проверка реальным аккаунтом и доставка писем учитываются отдельно.

## Откат

Сохранённый пакет релиза возвращает точные прежние образы и маршруты.
Не откатывать базу или записи согласий: этот выпуск не меняет схему.
Старая версия не проверяет совершеннолетие, поэтому при полном откате
закройте новые регистрации до возврата совместимой версии. Только старый web
с новым API выкладывать нельзя: старая форма не отправляет подтверждение возраста.
Обновлённый web со старым API не обеспечивает серверную возрастную проверку.

## Включение удаления аккаунта

Кнопку в кабинете включать последней. До этого read-only команда
`idctl legacy-cutover-seal` должна показать `sealed: true`: поле
`ready_to_seal` может стать `false` после появления новых записей аудита и не
показывает, был ли переход уже подтверждён. Не удаляйте записи аудита ради
изменения этого поля.

Если мешает `usid_audit_log`, команда `idctl legacy-cutover-audit-inventory`
показывает только число записей, известные типы событий и диапазон дат.
Она не выводит идентификаторы и содержимое журнала и ничего не меняет.
Для отдельного операторского разбора `--review-machine-actions` показывает
только короткие технические названия неизвестных событий; свободный текст
заменяется на `opaque`. Не публикуйте этот отчёт как пользовательские данные.
Одна сводка не доказывает происхождение записей и не разрешает их удаление:
сначала сохраните копию и отдельно разберите все непривязанные события.

Для рабочего сценария нужны маршрут `POST` и `OPTIONS`
`/api/v1/auth/account/deletions` к контейнеру `mutations`, отдельное задание
`/internal/jobs/recover-deletion`, ключ `ID_DELETION_OPERATION_KEY` и согласованно
включённые `ID_AUTH_DELETION_ROLLOUT_ENABLED`,
`ID_DELETION_JOBS_ROLLOUT_ENABLED`, `ID_WEB_DELETION_ENABLED`. Экспорт с
отложенной выдачей должен оставаться включённым в API, jobs и web. При
откате сначала скрыть кнопку и закрыть создание новых заявок, сохранив
фоновое задание для уже принятых заявок.

Перед открытием функции всем пользователям пройти путь на одноразовом аккаунте
в рабочем окружении: создать запрос на копию данных, подтвердить удаление,
проверить закрытие входа, доставку копии после удаления и конечное состояние
в YDB и объектном хранилище. Отдельно проверить повтор задания после сбоя.
Локальный браузерный сценарий и CI не заменяют этой проверки.

## Ограничения и следующие этапы

- Новые регистрации разрешены с 18 лет по заявлению пользователя; проверка
  документов не выполняется. Существующие аккаунты не удаляются.
- Исторические согласия и ограничения доступа сохраняются. Маркетинговой
  подписки в форме нет. Новые тексты документов не переписывают старые согласия.
- Публичные сведения об операторе: Mihhail Matvejev, РФ, admin@updspace.com.
  Полные сроки хранения, поставщики, адрес обращений и основания обработки
  требуют уточнения. Наличие страниц не доказывает соответствие GDPR или 152-ФЗ.
- Production admin и удаление аккаунта не включаются этим релизом. Экспорт ID
  не включает собственные данные Portal и других приложений.
- Локальный зашифрованный backup не защищает от потери всего сервера.
  Workstation/offsite выключен владельцем; данный выпуск его не включает.
  Свежий restore и реальный 24-часовой путь экспорта требуют отдельной приёмки.
